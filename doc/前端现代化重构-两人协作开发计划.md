## 一、项目概述与角色分工

### 1.1 项目目标

将现有 Streamlit 单体应用重构为现代化的 React + FastAPI 分布式架构，实现：

* 前端：React 18 + TypeScript + Vite

* 后端：FastAPI（技能树 API 8000 端口 + RAG API 8001 端口）

* 解耦 RAG 引擎与前端，实现独立部署与扩展

### 1.2 角色分工

| 角色           | 负责人 | 主要职责                         | 交付物                      |
| ------------ | --- | ---------------------------- | ------------------------ |
| **前端主导 (A)** | 姜美辰 | React 架构搭建、组件开发、前端集成         | frontend/ 完整代码           |
| **后端主导 (B)** | 安昱  | FastAPI 服务开发、RAG 引擎封装、SSE 实现 | server.py、rag\_server.py |

### 1.3 协作原则

1. **平等协作**：两人共同参与架构设计，关键决策需双方确认
2. **独立开发**：各自负责模块可独立开发，减少等待依赖
3. **持续集成**：每日合并到开发分支，保持代码同步
4. **文档先行**：接口文档、数据结构需提前约定

## 三、协作流程与规范

### 3.1 Git 分支管理策略

#### 分支命名规则

```
main                 // 主分支，始终保持可发布状态
├── develop          // 开发分支，整合所有功能
│   ├── feature/xxx  // 功能分支（个人开发用）
│   ├── feature/chat-frontend      // A：聊天前端
│   ├── feature/skill-tree-frontend // A：技能树前端
│   ├── feature/rag-api            // B：RAG API
│   └── feature/skill-tree-api     // B：技能树 API
├── bugfix/xxx       // Bug 修复分支
└── release/x.x.x    // 发布分支
```

#### 工作流程

```
1. 每天开始工作时：
   - 从 develop 拉取最新代码：`git pull origin develop`
   - 如有冲突，当时解决

2. 开发过程中：
   - 在 feature/xxx 分支开发
   - 频繁提交（每完成一个小功能）
   - 提交信息遵循规范（见下文）

3. 每日结束前：
   - 合并到 develop：`git checkout develop && git merge feature/xxx`
   - 如有冲突，冲突双方当时视频解决
   - push 到远程：`git push origin develop`

4. 功能完成后：
   - 创建 Pull Request
   - 另一人 Code Review
   - 合并到 develop
```

#### Commit 信息规范

```
<type>(<scope>): <subject>

type: feat | fix | docs | style | refactor | test | chore
scope: chat | skill-tree | rag | common | api

示例：
feat(chat): 实现聊天窗口消息展示
fix(skill-tree): 修复技能删除后列表未刷新的bug
docs(api): 更新RAG接口文档
refactor(common): 提取公共API请求hook
```

### 3.3 API 接口约定

#### 请求/响应格式

```typescript
// 统一响应格式
interface ApiResponse<T> {
  code: number;      // 0: 成功，其他: 失败
  message: string;   // 错误信息
  data?: T;          // 数据
}

// 分页响应
interface PaginatedResponse<T> {
  code: number;
  message: string;
  data: {
    items: T[];
    total: number;
    page: number;
    page_size: number;
  };
}

// SSE 流式响应格式
// Content-Type: text/event-stream
// data: {"token": "xxx"}
// data: {"token": "xxx"}
// ...
// data: [DONE]
```

#### 错误码规范

| 错误码  | 含义        | 处理方式            |
| ---- | --------- | --------------- |
| 0    | 成功        | -               |
| 1001 | 参数错误      | 前端表单校验 + 后端二次校验 |
| 1002 | 资源不存在     | 404 页面提示        |
| 2001 | RAG 模型未加载 | 提示用户先加载模型       |
| 2002 | RAG 生成失败  | 显示错误信息          |
| 5000 | 服务器内部错误   | 记录日志，返回通用错误     |

### 3.5 冲突预防与解决

#### 3.5.1 预防措施

1. **接口文档先行**：后端 B 提前定义接口，前端 A 基于文档开发，避免接口争议
2. **类型定义共享**：共用 `types/` 目录，任何变更需双方确认
3. **频繁集成**：每天至少合并一次，避免大范围冲突
4. **模块解耦**：各自负责模块独立，不轻易修改他人代码

#### 3.5.2 冲突解决流程

```
Step 1: 发现冲突
   - git push 被拒绝
   - 或 git pull 后出现 CONFLICT

Step 2: 保持冷静
   - 不要删除他人的代码
   - 不要强行覆盖

Step 3: 视频沟通
   - 发起屏幕共享
   - 共同查看冲突文件
   - 讨论保留方案

Step 4: 解决冲突
   - 保留必要的代码
   - 删除冲突标记
   - 添加测试验证

Step 5: 提交并通知
   - git add + git commit
   - git push
   - 群里通知对方
```

#### 3.5.3 常见冲突场景处理

| 场景       | 处理方式           |
| -------- | -------------- |
| 同时修改同一组件 | 协商合并，保留双方合理逻辑  |
| 接口字段变更   | 后端主导，前端配合修改    |
| 样式冲突     | 遵循代码规范，以 A 的为准 |

## 七、关键注意事项

### 7.1 技术注意事项

1. **SSE 实现**：后端使用 `StreamingResponse`，前端使用 `EventSource` 或 `fetch` + `ReadableStream`
2. **模型加载**：RAG 模型加载需异步处理，前端显示加载状态
3. **文件上传**：注意大小限制（建议 100MB），支持断点续传
4. **状态管理**：前端使用 Zustand，避免 Prop Drilling

### 7.2 协作注意事项

1. **不要轻易修改他人代码**：如需修改，先沟通
2. **保持分支同步**：每天开始先 pull，结束前 push
3. **接口变更要通知**：任何接口改动必须群里通知并更新文档
4. **保留沟通记录**：重要决策记录在文档中

### 7.3 质量注意事项

1. **提交前自测**：确保本地运行正常再提交
2. **测试用例**：核心功能必须有测试
3. **错误日志**：后端必须记录完整日志
4. **安全检查**：防止 SQL 注入、XSS 等安全问题
